# Pendientes de integración con el backend

El frontend está implementado contra el contrato de `/api/*` indicado en `PROMPT.md`. Como el backend no está activo, la compilación y las pruebas usan respuestas simuladas; **no se han validado llamadas reales** a Entra ID, API Manager, BFF ni microservicios. No hay datos de muestra presentados como datos reales: cada vista muestra carga, error o vacío.

## Diferencias comprobadas con el código backend local

- [ ] **API Manager y BFF.** El repositorio `pedidos360-backend` tiene `pedidos-service`, `productos-service` y `rabbit-admin-service`; no encontré `ms-pedidos360-bff`, `ms-pedidos360-report` ni `ms-pedidos360-audit`. Los controladores actuales exponen `/pedidos` y `/productos`, mientras el frontend llama a `/api/orders`, `/api/products`, `/api/reports/*`, `/api/audit/events` y `/api/health` en **una sola** `apiBaseUrl`. Implementar esas rutas en el gateway/BFF y mapearlas a los servicios, sin llamar desde Angular a los puertos 8081/8082. El gateway configurado actualmente puede no reconocerlas.

- [ ] **Métodos que faltan.** Los controladores actuales solo tienen GET lista y POST creación. Añadir GET/PUT `/api/orders/{id}`, PATCH `/api/orders/{id}/status`, PUT `/api/products/{id}` y PATCH `/api/products/{id}/stock`. PATCH debe responder el recurso actualizado, y POST el recurso con su `id`. GET detalle inexistente debe devolver 404.

- [ ] **Roles.** Mantener solo app roles `Admin` y `Cliente` en el claim `roles` del **access token** emitido para la API. `Operator` no es un rol; sus tareas y menú corresponden a Admin. `Customer` es solo la etiqueta visible para `Cliente`. Prioridad si hay ambos: Admin. La UI oculta acciones, pero el gateway/BFF debe imponer Admin para crear/editar/cambiar estado de pedidos, operar catálogo, consultar reportes/auditoría/evidencias; Cliente solo lee sus pedidos. Un usuario autenticado sin esos roles ve Dashboard/Perfil sin datos privados. El backend actual permite GET de todos los pedidos para ambos roles, lo que **filtra datos de otros clientes**: corregir antes de exponerlo a Cliente.

- [ ] **Propiedad de pedidos.** Agregar `customerId` = claim `oid` y `customerTenantId` = claim `tid` del Cliente propietario, como campos persistidos, indexados e inmutables salvo operación administrativa. La creación es solo de Admin; actualmente el formulario permite indicar el ID de Entra de la cuenta destinataria. Validar ese ID en el BFF, idealmente con una búsqueda/selección de clientes (endpoint aún no especificado). GET lista debe filtrar **en el servidor** por ambos campos para Cliente, antes de paginar; GET detalle debe devolver 403/404 si no es suyo. El frontend también rechaza registros ajenos o sin propietario. `cliente` (nombre libre) o correo no identifican propiedad. Migrar registros históricos con una tabla de correspondencia verificada; los ambiguos quedan sin dueño hasta revisar. No asignar por nombre coincidente.

- [ ] **Estados.** Definir enum `CREATED`, `ACCEPTED`, `IN_PROGRESS`, `COMPLETED`, `CANCELLED`. Al crear, el servidor asigna `CREATED`. Transiciones usadas por la interfaz: `CREATED → ACCEPTED | CANCELLED`, `ACCEPTED → IN_PROGRESS | CANCELLED`, `IN_PROGRESS → COMPLETED | CANCELLED`; los terminales no avanzan. Validar transición y concurrencia en el backend, responder 409 si cambió el estado. Migración clara: `PENDIENTE → CREATED`, `EN_PREPARACION → IN_PROGRESS`, `ENTREGADO → COMPLETED`. No hay equivalente antiguo claro para ACCEPTED/CANCELLED; un estado desconocido se muestra «SIN EQUIVALENCIA» y requiere decisión de datos. Un `CANCELLED` nunca se presenta como completado.

- [ ] **Pedido completo.** El modelo Java actual solo tiene `id, cliente, detalle, total, estado, fecha`. La API nueva debe devolver `id, customerName, customerId, customerTenantId, detail, total, status, createdAt, updatedAt?, history[], items[]`. Los adaptadores aceptan `cliente/detalle/estado/fecha` antiguos donde la equivalencia es clara, pero no inventan dueño, historial ni productos. `createdAt/updatedAt/changedAt` deben ser ISO 8601 con offset o UTC; el `LocalDateTime` sin zona actual es ambiguo al mostrar fechas en Santiago. `total` es CLP entero; definir redondeo y quién lo calcula. Al guardar, el frontend envía `customerName, customerId, customerTenantId, detail, total, items[]`, cada ítem con `productId, name, quantity, unitPrice`. Validar productos/stock/precio y recalcular el total en el servidor; las cifras del navegador no son autoridad. PUT edita datos; PATCH cambia el estado, nunca mediante PUT.

- [ ] **Historial.** Persistir por pedido eventos `{status, changedAt, actorName, actorRole}` ordenados del más reciente al más antiguo. Registrar creación y cada cambio con identidad del JWT, fecha del servidor y estado previo/nuevo. El pedido histórico actual no trae eventos: la UI indica que no hay historial y no crea uno ficticio. El `OrderCreatedEvent` actual de RabbitMQ incluye `orderId, customer, description, total, status, createdAt`, pero no propietario, ítems ni actor; versionar/extender el evento y añadir cambios de estado/cancelación para reportería y auditoría.

- [ ] **Catálogo y stock.** El `Producto` Java actual contiene `id, nombre, categoria, precio`; agregar `stock` entero no negativo y persistirlo. La lista espera `{id, name, category, price, stock}` (el frontend acepta los nombres españoles viejos para los cuatro campos existentes). Si `stock` falta, se muestra «No disponible» y no se permite ajustarlo; no se interpreta como cero. PATCH stock recibe `{delta: 1}` o `{delta: -1}`; aplicar ajuste atómico y devolver el producto, sin permitir negativos. El frontend usa lista, sin imágenes ni grid.

- [ ] **Paginación y filtros.** GET `/api/orders?status=&q=&from=&to=&page=&pageSize=` devuelve `{items: Order[], total, page, pageSize}`, con `page` desde 0. Filtrar en BFF antes de paginar y contar; `from/to` son fechas ISO `YYYY-MM-DD` inclusivas en zona `America/Santiago`; ordenar por fecha descendente e ID estable. Admin puede consultar todos, Cliente solo los suyos. El adaptador admite arrays legados para Admin con filtrado/paginación local temporal, pero los clientes requieren propiedad explícita. Evitar que `total` revele pedidos de otros usuarios.

- [ ] **CORS, scopes y permisos.** `SecurityConfig` actual permite GET/POST/PUT/DELETE/OPTIONS, pero **no PATCH**. Incluir PATCH en gateway y servicios y permitir `Authorization`/`Content-Type` desde el origen SPA real. El frontend conserva el scope existente `pedidos.read`; definir y conceder un scope de escritura (`pedidos.write`) si el gateway lo exigirá. En ese caso actualizar `apiConfig.scopes` en ambos environments y App Registration; el rol Admin por sí solo no reemplaza la autorización de scope. Los métodos nuevos de Spring Security deben tener reglas explícitas; el `anyRequest().authenticated()` actual dejaría PUT/PATCH sin restricción Admin.

- [ ] **Redirect URI y despliegue.** Registrar en Entra ID `http://localhost:4200/auth/callback` y `https://carlitos-a.github.io/pedidos360-frontend/auth/callback` como SPA, junto a los orígenes CORS pertinentes. El workflow de GitHub Pages ya copia `index.html` a `404.html` y compila con `--base-href /pedidos360-frontend/`; comprobar en despliegue el retorno a la ruta de callback. Configurar `apiBaseUrl` real de cada ambiente. Los enlaces de API Manager, RabbitMQ y Kafka están vacíos hasta conocer URLs; no se muestran como links activos.

## Datos del Dashboard y reportes

- [ ] GET `/api/reports/kpis?days=30` debe entregar `totalOrders`, `monthlySales`, `activeUsers`, `averageLeadTimeDays`, `pendingOrders`, `inProgressOrders`, `completedToday`, `totalSales`, `averageOrderValue`, `cancellationRate` (fracción entre 0 y 1), `completedOrders`, `byStatus` (objeto con conteos para los cinco estados) y `updatedAt` ISO. `pendingOrders` cuenta CREATED; `inProgressOrders` cuenta ACCEPTED + IN_PROGRESS; `completedToday` usa día de Santiago; `averageLeadTimeDays` mide CREATED→COMPLETED. Definir si pedidos cancelados se excluyen de ventas/ticket y documentarlo. Campos sin base de cálculo deben ser `null` para que la UI muestre «No disponible», nunca números inventados.

- [ ] GET `/api/reports/sales?days=365|30|...` devuelve `[{month: '2026-11', sales: 123456, orderCount: 42}]`. El Dashboard Admin grafica `orderCount` de los últimos 12 meses; Reportes grafica `sales`. En ambos casos faltan agregados en el backend actual.

- [ ] GET `/api/reports/lead-time?days=...` devuelve `[{month: '2026-11', days: 2.4}]` para pedidos completados. GET `/api/reports/top-products?days=...` devuelve `[{productId, name, units}]`; requiere ítems por pedido, inexistentes actualmente.

- [ ] Dashboard Admin también consulta `/api/orders?page=0&pageSize=5` para actividad reciente y listas por CREATED/ACCEPTED/IN_PROGRESS para integrar las tareas de Operator. Dashboard Customer usa solo `/api/orders` filtrado por su JWT: pedido más reciente, stepper y últimos pedidos. Si no hay propietario verificable, muestra error en vez de pedidos ajenos. No hay fixtures en producción.

- [ ] **Polling de Reportes:** al entrar, consultar en paralelo los cuatro endpoints; repetir cada 30 s mientras la ruta está activa. El selector cambia `days` y reinicia la serie; al salir se cancela. Cada ciclo usa timeout de 25 s y evita solaparse. «En vivo» indica última consulta correcta, no streaming por Kafka. Si falla, conservar la última lectura, mostrar «Sin conexión» y botón Reintentar. `updatedAt` del servidor indica frescura de los KPIs y «Última consulta correcta» muestra la hora local de recepción. Para tiempo real real, el servicio de reportes debe proyectar eventos Kafka y actualizar sus agregados.

## Auditoría

- [ ] Crear servicio de auditoría que persista eventos Kafka de tipos `ORDER_CREATED`, `ORDER_STATUS_CHANGED`, `ORDER_CANCELLED`, `PRODUCT_UPDATED`, `USER_LOGIN`. GET `/api/audit/events?user=&type=&from=&to=&page=&pageSize=` devuelve `{items:[{id,type,description,actorEmail,occurredAt}],total,page,pageSize}`. Ordenar por `occurredAt DESC, id DESC`; fechas ISO con zona. Filtrar `user` por correo del actor, `type` por enum y rango inclusivo en Santiago. Página desde 0, tamaño 20. «Cargar más» solicita la página siguiente y anexa sin duplicados; al cambiar filtros vacía el timeline. Un fallo permite reintentar la misma página. Registrar el usuario desde el JWT en el servidor, nunca desde el cuerpo enviado por el cliente. Definir retención y evitar datos sensibles en `description`; `USER_LOGIN` requiere evento de autenticación confiable de Entra/BFF, ya que un componente Angular no prueba que el login fue exitoso para el servidor.

## Evidencias: qué hace cada panel

- [ ] **Token decodificado.** MSAL obtiene el access token para la API; el frontend decodifica su payload para mostrar `iss, aud, scp, roles, upn, exp`. Un reloj local calcula la cuenta regresiva de `exp`. Esto es una lectura visual, **no** validación criptográfica. «Copiar token» solicita uno a MSAL y lo pone en el portapapeles; «Abrir en jwt.ms» abre la página sin token en la URL. El usuario decide si lo pega. Configurar el API para emitir los claims esperados; `upn` puede faltar en ciertos tenants.

- [ ] **Estado del despliegue.** GET `/api/health` debe responder, vía API Manager, `{services:[{name:'bff'|'orders'|'products'|'report'|'audit',status:'UP'|'DOWN'}]}`. Las etiquetas se configuran en `healthServices`. Frontend «CARGADO» solo indica que la SPA se cargó; no es health del hosting cloud. Si el agregado falla o no informa un servicio, mostrar error o «SIN DATOS», no UP ficticio. Los servicios internos no se consultan directamente desde el navegador. Proteger health para la vista Admin o definir una respuesta pública reducida.

- [ ] **Pruebas JWT.** Los cuatro botones llaman realmente `GET /api/orders`, con `HttpBackend` para saltarse `MsalInterceptor` y el interceptor que renueva 401. Válido: bearer obtenido de MSAL, esperado 200. Sin token: header ausente, esperado 401. Alterado: se cambia un bit significativo del último carácter de la firma JWT, esperado 401. Expirado: se usa un access token cuyo `exp` ya pasó; si no existe, el usuario puede pegarlo en un input oculto. Cambiar manualmente `exp` invalidaría la firma, por eso se rechaza en esta prueba. La tabla enseña el header **truncado**, esperado y recibido; un error de red/CORS se muestra sin código HTTP, no como 401. El código 401 demuestra rechazo, pero el motivo exacto (firma/expiración) solo se constata con logs/política del API Manager. El token pegado se limpia tras usarlo y no se guarda manualmente en localStorage.

- [ ] **Consolas.** URLs configurables en `environment*.ts`; enlaces vacíos se muestran como pendientes. Abrir consolas en otra pestaña con `noopener noreferrer`. Configurar URL de API Manager, RabbitMQ Management y Kafka-UI cuando existan; Microsoft Entra ID ya apunta a su consola general.
